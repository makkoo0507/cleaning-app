## 清掃依頼機能

**作成日:** 2026-06-27
**ステータス:** 設計確定・実装待ち

### 概要

民泊オーナーが LINE Mini App から清掃を依頼できる機能。管理者が依頼を確認し、承認または却下する。承認時に正式な案件としてスケジュールに登録される。

### データ設計

#### cleaning_requests テーブル（新規）

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | PK |
| contractor_id | uuid | 業者ID（FK） |
| property_id | uuid | 物件ID（FK） |
| requested_by | uuid | 依頼したオーナーのユーザーID（FK） |
| requested_date | date | 希望清掃日 |
| requested_start_time | time | 希望開始時刻（nullable） |
| note | text | オーナーからのメモ・変更希望（nullable） |
| status | text | `pending` / `approved` / `rejected` |
| rejection_reason | text | 却下理由（nullable、却下時のみ） |
| created_at | timestamp | |

#### jobs テーブル（変更）

| カラム | 型 | 説明 |
|---|---|---|
| request_id | uuid | FK → cleaning_requests（nullable） |

- 依頼から作成された案件のみ `request_id` を持つ
- 手動作成の案件は `request_id = null`

### 機能仕様

#### 1. オーナー側（LINE Mini App）

**場所:** スケジュール確認メニュー内に「依頼する」ボタンを追加

**依頼フォーム:**
- 日付（必須、オーナーが選択）
- 参考情報として以下を表示（変更不可）
  - 物件のデフォルト開始時刻
  - 物件のデフォルト請求金額
- メモ欄（任意）：時間変更希望や特記事項を記入

**送信後:** `cleaning_requests` に `status = pending` で登録

#### 2. 管理者側（管理 Web アプリ）

##### スケジュール画面への表示

- リスト・週・月の全ビューに依頼（pending）を表示
- **アンバー系の背景色**で通常の案件と視覚的に区別
- 依頼カードに表示する情報：物件名・希望日時・オーナー名・メモ

##### 承認

1. 「承認」ボタンを押す
2. 案件新規作成ページへ遷移（依頼データをプリフィル）
   - 物件、清掃日、開始時刻、請求額・支払い額がデフォルト値でセット
   - 修正可能
3. 保存すると `jobs` レコードが作成され `jobs.request_id` で依頼と紐付け
4. `cleaning_requests.status` が `approved` に更新

##### 却下

1. 「却下」ボタンを押す
2. 理由記入モーダルが開く（任意入力）
3. 送信すると `cleaning_requests.status` が `rejected`、`rejection_reason` に理由を保存
4. オーナーに LINE 通知（理由を含む）

##### ダッシュボード

- 要対応セクションに未対応の依頼（pending）件数を表示（未アサインと同様）

### 通知

| タイミング | 送信先 | 内容 |
|---|---|---|
| 依頼受付時 | 管理者（LINE通知 or ダッシュボード） | 新着依頼の通知 |
| 却下時 | 依頼したオーナー | 却下理由を含むLINEメッセージ |
| 承認・案件確定時 | 依頼したオーナー | 既存の案件作成通知と同様 |

### 実装順序（案）

1. DBマイグレーション（`cleaning_requests` テーブル作成・`jobs.request_id` 追加）
2. 管理画面スケジュール表示への依頼の混在（アンバー背景）
3. 承認UI（案件作成ページへの遷移・プリフィル・request_id 紐付け）
4. 却下UI（理由記入モーダル・LINE通知）
5. LINE Mini App 依頼フォーム（オーナー側）
6. ダッシュボード要対応セクションへの依頼件数追加

## 写真共有機能

**作成日:** 2026-06-28
**ステータス:** 設計確定・実装待ち

### 概要

清掃完了後に清掃者が写真をアップロードし、業者が確認・選別して、オーナーへ LINE で共有する機能。
現状の「清掃者 → LINE → 業者 → Google Drive → オーナー」という手動フローを置き換える。

### 現状フローと課題

```
現状:
1. 清掃者がLINEで写真を業者に送付
2. 業者が必要な写真を端末に保存
3. 業者がGoogle Driveにアップロード
4. Google Drive のURLを手動メッセージでオーナーに共有

課題:
- 4ステップの手動作業が必要
- Google Driveの管理が必要
- LINEを離れてしまう
```

### 新フロー

```
【清掃者 / LIFF】
  ├─ 清掃中・完了後どちらでも写真アップ可
  └─ 「完了」ボタン → 管理画面に"完了"表示（オーナーへは通知しない）

【業者 / 管理画面】
  ├─ 案件詳細で全写真を確認
  ├─ オーナーに共有する写真をチェックして選別
  ├─ 共有メモ（既存フィールド）に報告メッセージを記入
  └─ 「オーナーに報告」ボタン →
       LINE メッセージ送信（共有メモ本文 + 「写真を見る」ボタン）

【オーナー / LINE・LIFF】
  └─ 「写真を見る」タップ → LIFF フォトギャラリーページ
       （share_with_owner = true の写真のみ表示）
```

### 通知フローの変更

| タイミング | 現状 | 変更後 |
|---|---|---|
| 清掃完了 | オーナーに自動通知 | **通知なし**（管理画面のみ反映） |
| 業者が「報告」ボタンを押す | なし | **オーナーに通知**（本文＋写真リンク） |

#### jobs テーブル（変更）

| カラム | 型 | 説明 |
|---|---|---|

### ストレージ設計

#### Supabase Storage

- バケット名: `cleaning-images`
- アクセス: プライベート（RLS で制御）

#### RLS 方針

| ロール | 権限 |
|---|---|
| 清掃者（cleaner） | アサインされている案件の画像をアップロード・閲覧 |
| 業者スタッフ（contractor_admin / contractor_vendor） | 自社案件の全画像を閲覧・削除 |
| オーナー（contact） | share_with_owner = true の自物件画像のみ閲覧 |

### 費用・パフォーマンス対策

#### ストレージ費用（Freeプランのまま運用可能）

60日で自動削除するため、常時の保存容量は直近60日分のみ。

常時保存量 = 月間案件数 × 12MB（30枚×400KB） × 2ヶ月（60日分）

1案件あたりの上限: 30枚（超過時はアップロード不可）

| 月間案件数 | 1案件あたり | 常時保存量 | 状況 |
|---|---|---|---|
| 月10案件 | 30枚 × 400KB = 12MB | 約240MB | 余裕あり |
| 月20案件 | 30枚 × 400KB = 12MB | 約480MB | 余裕あり |
| 月30案件 | 30枚 × 400KB = 12MB | 約720MB | 余裕あり |
| 月40案件 | 30枚 × 400KB = 12MB | 約960MB | ほぼ上限 |
| **月43案件** | 30枚 × 400KB = 12MB | **約1,032MB** | **Free上限（1GB）到達** |

月43案件を超えたタイミングで Proプラン（$25/月・100GB）への移行が必要。

#### クライアント側圧縮（Proプラン不要にするため）

アップロード前にブラウザ（Canvas API）で変換:
- 長辺: 最大 1200px
- 形式: JPEG
- 品質: 80%
- 結果: 1枚あたり 300〜500KB（元の iPhoneカメラ写真は 5〜8MB）

#### ページ表示速度

- 一覧は CSS でサムネイルサイズに縮小表示（別ファイル不要）
- タップで原寸表示
- 遅延ロード（lazy loading）を適用

### 保存期間・バックアップ

#### 自動削除

- 保存期間: **60日**
- 削除方法: 既存のリマインダーと同様の Edge Function + pg_cron で日次実行
- 削除対象: `created_at < now() - interval '60 days'` の cleaning_images
  - Supabase Storage から削除
  - DB レコードから削除

#### バックアップ（削除前にダウンロード）

削除7日前から管理画面の案件詳細にバナー表示:
「この案件の写真は XX日後に削除されます。必要な場合はダウンロードしてください。」

#### ダウンロード機能

| 機能 | 業者（管理画面） | オーナー（LIFF） |
|---|---|---|
| 個別ダウンロード | ✓ | ✓ |
| まとめて ZIP ダウンロード | ✓（全写真） | ✓（共有写真のみ） |

ZIP 生成: クライアント側で JSZip を使用（サーバー負荷なし）

## iCal連携

**作成日:** 2026-07-22
**ステータス:** 設計済み・未実装

### 概要

サイトコントローラー・OTA が提供する iCal フィードを定期的に取得し、チェックアウト日に清掃ジョブを自動生成する機能。

### OTA / サイトコントローラーの対応状況

| サービス | iCal エクスポート | 備考 |
|---|---|---|
| Airbnb | ✅ 対応 | `airbnb.com/calendar/ical/{ID}.ics?s={TOKEN}` |
| VRBO / HomeAway | ✅ 対応 | 30 分ごとにポーリング |
| 楽天トラベル（Oyado） | ✅ 対応 | TL-リンカーン併用中は使用不可 |
| Vacation STAY | ✅ 対応 | |
| Booking.com | ⚠️ エクスポートのみ | 2025年3月以降 外部からのインポート受付を制限。ダブルブッキング防止には不向き |
| じゃらん | ❌ 直接対応なし | AirHost 等チャネルマネージャー経由が必要 |
| Beds24 | ✅ 対応 | エクスポート・インポート両対応 |
| Smoobu | ✅ 対応 | 双方向 iCal 同期 |
| TL-リンカーン | ❌ 非対応 | XML 接続のみ・iCal 併用禁止 |

### iCal の技術仕様

#### VEVENT の構造（民泊予約の典型例）

```ical
BEGIN:VEVENT
UID:HMXXXXXXXX@airbnb.com          ← 予約の一意ID（重複排除に使用）
DTSTART;VALUE=DATE:20250715        ← チェックイン日（全日イベント・包含）
DTEND;VALUE=DATE:20250720          ← チェックアウト日（全日イベント・非包含）
SUMMARY:Reserved                   ← ゲスト名は非公開（プライバシー保護）
DESCRIPTION:予約番号・リスティング名等
END:VEVENT
```

#### 日付の解釈

- `DTSTART` = チェックイン日（当日を含む）
- `DTEND` = チェックアウト日（当日を含む・最終泊の翌日ではない）
  - 例: `DTEND:20250720` → 7/20 チェックアウト → **清掃日 = 7/20**

#### OTA 別 SUMMARY

| OTA | SUMMARY の値 |
|---|---|
| Airbnb | `Reserved` / `Airbnb (Not available)` |
| Booking.com | `CLOSED` / `Booking.com (Not available)` |
| VRBO | `Reserved` / `Vrbo Reservation` |
| ブロック（手動） | `Not available` / `Blocked` |

#### 更新頻度

- iCal はポーリングベースのため **15 分〜数時間の遅延** が発生する
- リアルタイム反映が必要な場合は API（XML）接続が必要

### データ設計

#### 新規テーブル

```sql
-- 物件ごとの iCal フィード管理
CREATE TABLE ical_feeds (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  contractor_id   UUID NOT NULL REFERENCES contractors(id) ON DELETE CASCADE,
  property_id     UUID NOT NULL REFERENCES properties(id) ON DELETE CASCADE,
  name            TEXT NOT NULL,   -- "Airbnb", "VRBO" など表示名
  url             TEXT NOT NULL,   -- iCal フィード URL
  last_synced_at  TIMESTAMPTZ,
  last_error      TEXT,            -- 直近の同期エラー内容（成功時は null）
  created_at      TIMESTAMPTZ DEFAULT now()
);

-- 取得済み予約データ（iCal の VEVENT をそのまま保存）
CREATE TABLE ical_bookings (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  feed_id       UUID NOT NULL REFERENCES ical_feeds(id) ON DELETE CASCADE,
  property_id   UUID NOT NULL REFERENCES properties(id) ON DELETE CASCADE,
  uid           TEXT NOT NULL,      -- VEVENT の UID（一意キー）
  dtstart       DATE NOT NULL,      -- チェックイン日
  dtend         DATE NOT NULL,      -- チェックアウト日（= 清掃日）
  summary       TEXT,               -- "Reserved" 等
  missing_count INT NOT NULL DEFAULT 0,  -- 連続して消えていた同期回数（2以上でキャンセル）
  created_at    TIMESTAMPTZ DEFAULT now(),
  UNIQUE (feed_id, uid)             -- 同一フィード内で重複排除
);
```

#### 既存テーブルの変更

```sql
-- jobs テーブルに source カラムを追加（iCal 由来の識別）
ALTER TABLE jobs ADD COLUMN source TEXT NOT NULL DEFAULT 'manual';
-- 値: 'manual'（手動作成）| 'ical'（iCal 連携による自動作成）

-- ical_bookings との紐付け

```

#### `jobs.status` に `cancelled` を追加

現状の `JobStatus` は `scheduled | in_progress | completed` の3種類。iCal 連携のキャンセル検知に合わせて `cancelled` を追加する。

```sql
-- PostgreSQL の ENUM を使っている場合は ALTER TYPE、TEXT の場合は変更不要
-- 本プロジェクトは TEXT 型のため、アプリ側の型定義のみ変更
```

```ts
// lib/database.types.ts
export type JobStatus = "scheduled" | "in_progress" | "completed" | "cancelled";

export const JOB_STATUS_LABEL: Record<JobStatus, string> = {
  scheduled: "予定",
  in_progress: "作業中",
  completed: "完了",
  cancelled: "キャンセル",

```

- `cancelled` のジョブは一覧上でグレーアウト表示する
- 手動キャンセルの UI は今回は追加しない（iCal 由来の自動キャンセルのみ）

### 同期処理（Edge Function）

#### `supabase/functions/sync-ical/index.ts`

```
処理フロー:
1. ical_feeds テーブルから全フィードを取得
2. 各フィードの URL に fetch（並列実行）
   - fetch 失敗（タイムアウト・404等）の場合は ical_feeds.last_error に記録し、スキップ
   - fetch 成功時は ical_feeds.last_error を null にクリア
3. レスポンスの .ics テキストを VEVENT 単位でパース
4. uid + feed_id をキーに ical_bookings へ upsert
5. 【新規予約】前回同期にはなく今回追加された ical_bookings を検出
   → dtend（チェックアウト日）が今日以降のもののみ処理対象（過去分はスキップ）
   → dtend（チェックアウト日）を scheduled_date として jobs を INSERT
      - cleaner_id: null（未アサイン）
      - status: 'scheduled'
      - source: 'ical'
      - ical_booking_id: 紐付け
   → 同日・同物件のジョブが既に存在しても重複作成する（業者が手動整理）
6. 【キャンセル検知】前回同期にはあったが今回消えた ical_bookings を検出
   → ical_bookings.missing_count をインクリメント
   → missing_count が 2 以上になった時点で紐付いている jobs の status を 'cancelled' に更新
   → 再び現れた場合は missing_count を 0 にリセット（jobs は cancelled のまま・業者が手動で戻す）
7. ical_feeds.last_synced_at を更新
```

### テスト方法

#### ステップ1: 静的 .ics ファイルでのローカルテスト

`next/public/test.ics` に .ics ファイルを作成し、`http://localhost:3000/test.ics` を iCal URL として物件に登録する。

```ical
BEGIN:VCALENDAR
VERSION:2.0

BEGIN:VEVENT
UID:test-001@example.com
DTSTART;VALUE=DATE:20260801
DTEND;VALUE=DATE:20260803
SUMMARY:Reserved
END:VEVENT

END:VCALENDAR
```

Edge Function は curl で手動実行：

```bash
curl -X POST http://127.0.0.1:54321/functions/v1/sync-ical \
  -H "Authorization: Bearer {SERVICE_ROLE_KEY}"
```

確認するシナリオ：

| シナリオ | 操作 |
|---|---|
| 新規予約 → ジョブ作成 | VEVENT を追加して同期 |
| 過去日付はスキップ | dtend を過去日付にして追加・ジョブが作成されないことを確認 |
| キャンセル検知（1回目） | VEVENT を削除して同期 → missing_count = 1・ジョブは scheduled のまま |
| キャンセル検知（2回目） | そのまま再同期 → missing_count = 2・ジョブが cancelled に更新 |
| 再出現 → missing_count リセット | 削除した VEVENT を戻して同期 |
| 重複ジョブ作成 | 同日・同物件のジョブが既にある状態で同期 → 両方存在することを確認 |
| エラーバッジ表示 | URL を存在しないパスに変更して同期 → 管理画面でエラーバッジ確認 |

#### ステップ2: 実際の OTA フィードで結合確認

ローカルテストで全シナリオ確認後、実際の Airbnb 等のフィード URL を登録して動作確認する。文字コード・改行コード・UID 形式など実データ固有の問題を検出する。

### 未対応・今後の検討事項

- **ダブルブッキング防止**: iCal は最大 1 時間の遅延があるため、高稼働物件では API 接続を推奨
- **Booking.com**: 2025年3月以降インポート制限あり。連携する場合は Beds24 等チャネルマネージャー経由が必要
- **じゃらん**: AirHost 等のサイトコントローラーが必要。iCal 直接連携は困難
